# Laboratorio v1.0 (S-9): cambiar la llave del 2FA sin dejar a nadie fuera

> Igual que los anteriores: **la falla**, **cómo se da**, **qué la evita** y **qué prueba lo demuestra**. Pruebas: `api/src/auth/two-factor/secret-box.spec.ts` (llavero, formato v1 heredado, kid), `rotate-key.spec.ts` (lotes, carrera, filas sin llave, `--check`), `key-ring-check.spec.ts` (el aviso al arrancar) y `api/src/config/env.spec.ts`. Más el **ensayo en vivo** de la §D.
>
> Los secretos del 2FA se guardan cifrados con `TOTP_ENCRYPTION_KEY` (AES-256-GCM, v0.5). Hasta v1.0 esa llave **no se podía cambiar**: cambiarla dejaba todos los secretos ilegibles. Una llave que no se puede rotar es una llave que, si se filtra, se queda filtrada para siempre.

## A. El diseño: un llavero, no una llave

- **Llave actual** (`TOTP_ENCRYPTION_KEY`): cifra todo lo nuevo y descifra. **Llaves anteriores** (`TOTP_ENCRYPTION_KEYS_OLD`, separadas por comas): **solo descifran**, y solo existen mientras dura una rotación.
- **Formato `v2.<kid>.<iv>.<etiqueta>.<datos>`.** El `kid` son 8 caracteres de un HMAC-SHA256 de la llave: dice **con cuál** se cifró sin revelar nada de ella (no se puede invertir). Con el kid, descifrar es directo y saber qué falta rotar es una comparación de texto.
- **Formato `v1` (sin kid), el de v0.5 a v0.12:** se sigue leyendo, probando la actual y luego las anteriores. Probar es seguro: con una llave equivocada GCM **falla** (la etiqueta de 128 bits no coincide), no devuelve basura.
- El AAD sigue siendo el id del usuario: un secreto copiado a la fila de otra persona no descifra, con ninguna llave.

## B. Las fallas y lo que las evita

| # | Falla | Cómo se da | Qué la evita | Prueba |
|---|---|---|---|---|
| 1 | **Todos fuera al cambiar la llave** | Se cambia `TOTP_ENCRYPTION_KEY` y los secretos guardados ya no abren | El llavero: la vieja sigue descifrando hasta que se re-cifra todo | `secret-box.spec.ts`, ensayo §D paso 3 |
| 2 | **Re-cifrar pisa un secreto recién creado** | La persona reactiva su 2FA (`/2fa/setup`) justo entre que la rotación lee su fila y la escribe | «Compara y cambia»: se escribe solo si `secret_enc` sigue siendo el que se leyó; si cambió, ya viene con la llave actual y no se toca | `rotate-key.spec.ts` (la carrera, con falla sembrada: sin la comparación, la prueba falla) |
| 3 | **Retirar la vieja antes de tiempo** | Se quita `TOTP_ENCRYPTION_KEYS_OLD` con filas aún sin re-cifrar | `--check` sale con 0 solo cuando ninguna fila depende ya de una llave anterior (3 si faltan, 4 si alguna no abre) | `rotate-key.spec.ts`, ensayo §D |
| 4 | **Una API con la llave equivocada arranca en silencio** | Rotación a medias, llave vieja retirada antes de tiempo, un `.env` de otra máquina: cada persona con 2FA recibe «código incorrecto» y nadie lo relaciona con la llave | Al arrancar, la API hace la revisión en seco y escribe **ERROR [2FA] N de M secretos NO abren** (o un aviso si la rotación está a medias). No impide arrancar: el resto del sitio, y quien entra con un código de recuperación, siguen funcionando | `key-ring-check.spec.ts`; **lo destapó el ensayo** (§D paso 6) |
| 5 | **Una llave repetida en el llavero** | La actual copiada también como vieja (p. ej. si `--rotar-totp` se corta a medias) | El llavero se niega a construirse y la API no arranca: falla visible, sin tocar datos | `secret-box.spec.ts` |
| 6 | **Falsificar el kid para forzar otra llave** | Cambiar el kid de una fila | Con la llave equivocada GCM falla: el kid solo elige qué llave **probar** | `secret-box.spec.ts` |
| 7 | **Filtrar llaves o secretos en mensajes** | Una llave mal escrita en `TOTP_ENCRYPTION_KEYS_OLD`, un informe de la rotación | Los mensajes nombran la variable, nunca el valor; el comando imprime conteos, el kid (público) y como mucho 20 ids de usuario | `env.spec.ts` |
| 8 | **Una rotación sin rastro** | Nadie sabe cuándo se cambió la llave | Entrada de auditoría `totp_key_rotated` (actor y destino nulos: la hace el sistema), con el número de filas y el kid | `rotate-key.spec.ts`, ensayo §D |

**Lo que NO resuelve, y hay que saberlo:** los **respaldos de la base hechos antes de rotar** siguen cifrados con la llave vieja. Conserva la vieja (aparte, igual que la actual) **mientras conserves esos respaldos**. Y si la llave actual se pierde sin copia, los secretos no se recuperan: esas personas entran con un código de recuperación y vuelven a activar el 2FA (S-10 trata a quien perdió también esos códigos).

## C. Procedimiento

**Producción** (secretos en `secrets/`, ver `docker-compose.prod.yml`):

```bash
./scripts/crear-secretos.sh --rotar-totp     # la actual pasa a totp_encryption_key_old; se crea una nueva
#   → respalda la NUEVA aparte de la base (y conserva la vieja mientras haya respaldos que la necesiten)
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d api    # arranca con las dos
docker compose -f docker-compose.prod.yml run --rm api sh /arranque.sh node dist/cli/rotar-llave-totp.js          # re-cifra
docker compose -f docker-compose.prod.yml run --rm api sh /arranque.sh node dist/cli/rotar-llave-totp.js --check  # debe salir 0
./scripts/crear-secretos.sh --retirar-totp-vieja
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d api
```

**Desarrollo:** pon la nueva en `TOTP_ENCRYPTION_KEY` y la vieja en `TOTP_ENCRYPTION_KEYS_OLD` (en `.env`), `docker compose up -d api`, y `docker compose exec api npx tsx src/cli/rotar-llave-totp.ts` (con `--check` para revisar). Luego vacía `TOTP_ENCRYPTION_KEYS_OLD`.

`--rotar-totp` se niega a empezar si ya hay una llave vieja: una rotación a la vez, o las filas cifradas con la más antigua quedarían sin llave.

## D. El ensayo en vivo (2026-11-20, sistema de desarrollo)

Con la base de desarrollo, que tenía **62 filas en formato `v1`** creadas por las e2e con el código anterior (el dato heredado real) y una cuenta nueva con 2FA en `v2`. Las llaves se pasaron por variables del shell, sin tocar el `.env` ni imprimirlas.

| Paso | Qué se hizo | Resultado |
|---|---|---|
| 1 | Migración `totp_key_rotated` | Aplicada |
| 2 | Cuenta nueva con 2FA | Fila `v2` con la llave del `.env` |
| 3 | API con llave nueva + la del `.env` como vieja; entrar con código | 200 (descifra con la vieja) |
| 4 | `--check` · rotar · `--check` | 63 pendientes, salida 3 · 63 re-cifradas, 0 en carrera, 0 sin llave · 0 pendientes, salida 0 |
| 5 | API **solo** con la nueva; entrar con código | 200 |
| 6 | API **solo** con la vieja (prueba inversa); entrar con código | **401**: los datos de verdad cambiaron de llave. `--check` sale 4 y lista las 63. **La API había arrancado sin decir nada** → falla §B-4, corregida con la revisión al arrancar |
| 7 | Auditoría | `totp_key_rotated`, actor y destino nulos, `filas=63 kid=…` |
| 8 | Rotar de vuelta a la llave del `.env` (segunda rotación seguida) y entrar | 63 re-cifradas; 200. Entorno como estaba |
| 9 | API con una llave al azar | `ERROR [2FA] 63 de 63 secretos del 2FA NO abren…` en el log; con la correcta, silencio |
