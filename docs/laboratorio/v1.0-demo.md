# Laboratorio v1.0: la demo de 24 h

> Igual que los anteriores: **la falla**, **cómo se da**, **qué la evita** y **qué prueba lo demuestra**. Pruebas unitarias: `api/src/config/demo-env.spec.ts`, `api/src/demo/demo.service.spec.ts`, `api/src/demo/demo-sweeper.spec.ts`, más los casos de cuenta vencida en `auth.service.spec.ts`, `google-accounts.spec.ts` y el cupo en `analyses.service.spec.ts`. Contra el sistema vivo: `api/test/e2e/demo.e2e-spec.ts` (9) y `web/test/demo.spec.ts` (Chrome), con la demo encendida.
>
> La demo (PLAN_DESARROLLO.md §6) deja que **cualquiera** se registre y pruebe todo. Eso es justo lo que la vuelve un blanco: un formulario abierto a internet que acepta archivos y gasta CPU. Cada regla de abajo existe porque, sin ella, alguien con un script podría llenar la base, el disco o el worker, o dejar datos de personas reales en un sitio de estudio.

## A. Cómo se enciende y cómo se prueba

| Dónde | `DEMO_MODE` | Vida de una cuenta | Tope global |
|---|---|---|---|
| Desarrollo normal (`docker compose up`) | apagada | permanente | — |
| Prueba de la demo (`-f docker-compose.demo.yml`) | encendida | **90 s** | **3** |
| Producción (`docker-compose.prod.yml`) | encendida por omisión | **24 h** (la API no arranca con otra cifra) | 50 (`DEMO_MAX_ACCOUNTS`) |

```bash
docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d api   # enciende la demo
(cd api && npm run test:e2e -- demo) && (cd web && npx playwright test demo)
docker compose up -d api                                                     # de vuelta al modo normal
./scripts/preparar-ejemplos.sh   # los datos de ejemplo que la pantalla ofrece para descargar (antes de construir web)
```

## B. Las fallas y lo que las evita

| # | Falla | Cómo se da | Qué la evita | Prueba |
|---|---|---|---|---|
| 1 | **Llenar la base registrando correos** | Un script registra miles de cuentas | **Tope global** de cuentas vivas, contado **con candado** (`pg_advisory_xact_lock`) dentro de la transacción que crea la cuenta: dos altas a la vez no pueden contar «49» las dos. Vale para el registro, Google y las cuentas que crea un admin | `demo.service.spec.ts`; e2e «tope global» |
| 2 | **Perder el enlace por llegar tarde** | Pides cuenta con lugar; cuando abres el correo la demo ya se llenó | El 503 **deshace** la transacción: el enlace no se marca usado y sirve al liberarse un lugar. La pantalla ofrece «Reintentar con este enlace» | e2e «el MISMO enlace crea la cuenta» (nunca un 400) |
| 3 | **El tope delata a otros** | Un 503 que dijera «quedan 2 lugares» o un `/api/demo` con el conteo | El mensaje es fijo y `/api/demo` publica solo la configuración; el conteo no sale de la base | e2e (claves exactas de `/api/demo`) |
| 4 | **Entrar con una cuenta vencida** | El barrido corre cada 15 min: entre que vence y que se borra, la cuenta sigue en la base | **Vencida = desactivada** en todos los lugares que miran `disabledAt`: la guarda de cada petición, la renovación de sesión, el login (que lo anota en la bitácora como `expired`), el 2FA y Google | e2e «vencida» (con **falla sembrada**: quitando el filtro de la guarda, la prueba falla) |
| 5 | **Archivos huérfanos en el disco** | Borrar la fila deja los bytes; si la API se cae a la mitad, nadie los recuerda | El barrido borra **primero los bytes, después la fila** (en cascada). Si se cae a la mitad, la fila sigue y la próxima vuelta termina | `demo-sweeper.spec.ts` (orden); e2e mira **dentro del volumen** que no quede nada |
| 6 | **Borrar un archivo que el worker está leyendo** | El barrido llega mientras el worker revisa | La cuenta se salta esa vuelta: el archivo se marca `deleteRequestedAt` (el worker descarta su resultado) y se borra en la siguiente | `demo-sweeper.spec.ts` |
| 7 | **Ocupar al worker sin fin** | Subir, borrar y volver a subir (el tope de 10 archivos es «a la vez», no por día) | **Cupos de 24 h por cuenta** en Redis (`INCR` atómico con vigencia `NX`): 30 subidas y 20 análisis. **Borrar no devuelve el cupo**; solo se devuelve si la acción no llegó a ocurrir (409, cola caída) | `demo.service.spec.ts`; e2e (la 31.ª subida y el 21.º análisis son 429) |
| 8 | **Saltarse la casilla «sin datos reales»** | La casilla está en la pantalla; con `curl` no hay pantalla | La exige la **API**: sin `noRealData=true`, 400. Multer acepta **un** campo de texto de 16 bytes; otro nombre lo rechaza la validación | e2e (sin campo, `false`, valor raro y campo extra: 400) |
| 9 | **Una demo que dura más de lo prometido** | Un `.env` con `DEMO_ACCOUNT_TTL_S` de una semana | En producción la API exige 86 400 s; en desarrollo solo se puede **acortar** | `demo-env.spec.ts` |
| 10 | **Borrar cuentas que no son de la demo** | Un error en el barrido | Solo entran cuentas con `expires_at` ya pasado; las sembradas y las de fuera de la demo lo tienen en null. Y la fila se borra condicionada a «sigue vencida» en la misma sentencia | `demo-sweeper.spec.ts`; e2e (el admin sembrado tiene `expiresAt: null`) |
| 11 | **Una cuenta que nace vencida** | Un reloj mal puesto o un error de código | `CHECK (expires_at > created_at)` en la base | migración `20261120200000_demo_accounts` |

## C. Lo que la pantalla muestra

- **Registro:** «Cuenta de prueba: se borra con todo lo que subas 24 horas después de confirmar tu correo», con los límites (salen de `/api/demo`, no están escritos a mano).
- **Todas las pantallas con sesión:** el **aviso fijo** (se queda arriba al desplazarse) con la fecha y hora del borrado en la zona de quien lo lee y «Quedan 23 h 41 min». La fecha la da la API; el reloj del navegador solo resta, así que un reloj mal puesto mueve la cuenta regresiva, **nunca el borrado**. No es una región «viva»: un lector de pantalla no anuncia cada minuto.
- **Mis archivos:** la casilla obligatoria (se desmarca tras cada subida: se confirma archivo por archivo) y los **datos de ejemplo** para descargar: el café ficticio, sus gastos, CFDI sintéticos y el reporte en PDF.

## D. Lo que NO hace (a propósito)

- **No impide registrar correos ajenos:** el registro sigue siendo el de v0.2 (el enlace llega al dueño del correo, sin enumeración). El tope por IP y por destinatario de v0.2 sigue aplicando.
- **El tope global se puede agotar a propósito** (un script con 50 correos válidos deja la demo llena 24 h). Es una negación de servicio de la DEMO, no de los datos: el precio de no pedir nada más que un correo. Si pasara, se baja la vida o se sube el tope sin tocar código.
- **Los cupos viven en Redis:** si Redis se vacía, se reinician. Es aceptable (lo que protegen es CPU, no datos) y Redis es también la cola: si se cae, no hay subidas.
